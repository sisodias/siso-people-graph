J1 — Is canonical selection the right policy? Blocking

First: the brief's description of the policy does not match the code

The dispatch describes the resolver as preferring "registry/curated rows, then authority/book/platform origin, then strong-ID count, then lexical id." No such logic exists. I grepped the whole package: the words registry, curated, authority and strong_id appear nowhere in any selection path. The actual policy, query_v3/resolver.py:388-427 @ 3d648aa, is three rules:

  1. Liveness first — a row with state='merged' can never win while a live row exists.
  2. Applied winner — among live rows, one that something merged into beats an untouched peer.
  3. Lexical — otherwise sorted(live)[0].

Rule 1 is genuinely good and non-obvious. The docstring records that it was found the hard way: a 12-long merge chain resolved to bk:chain-1, a superseded row, while the only live row was ignored. Ordering liveness ahead of winner-ness fixes that. Credit where due — that is exactly the kind of bug that ships silently.

The blocking problem: in production, the policy is rule 3

Rules 1 and 2 both depend on person.merged_into. The baseline measured the shipped asset directly:

merged_into non-null = 0. state='merged' = 0. identity_claim = 0 rows.

So on production data there are no merged rows and no applied winners. Every cluster is "all rows live, none a winner", and selection collapses to sorted(members)[0] — pure alphabetical ID order. I verified this against the PR's own fixtures rather than inferring it:

seed=[gh:lovelace] -> canonical: bk:lovelace   members: ['bk:lovelace','gh:lovelace']
  bk:lovelace: origin=book   state=linked
  gh:lovelace: origin=github state=linked
  # both live, no merged_into, winners empty -> lexical smallest wins

And SISO's person IDs are prefixed by origin. So alphabetical order is an origin hierarchy, arrived at by accident:

bk:  <  crates:  <  gh:  <  registry:  <  yt:

Books beat crates beat GitHub beat registry beat YouTube — because "b" sorts before "g", not because anyone decided books are more authoritative. Note the irony: the brief believed registry/curated rows were preferred; lexically registry: loses to bk:, crates: and gh:. The intended policy and the actual policy are close to opposites.

What breaks when it is wrong

The canonical ID is what every downstream consumer stores, cites and links. Choosing it by prefix spelling means:

  • The richest row usually loses. The baseline's population shape is 245,171 GitHub rows vs 35,363 book rows. A gh: row with 40 content edges yields its identity to a bk: row with 1, because "b" < "g". who() already ranks matches by content_count (engine.py:265) — the engine knows which row is richer and the resolver ignores it.
  • It is silently unstable. Re-prefixing a source, or adding arxiv:, reshuffles canonical IDs across the corpus with no decision recorded and no diff to review.
  • It contradicts the module's own thesis. The file argues at length that it must never decide identity, only apply decisions. But picking the canonical ID is a decision, and here it is made by string sort with no evidence attached — while every other output in this PR carries a provenance grade. The one unattributed judgement in an evidence-first surface is this one.

The docstring calls it "deterministic policy, not a truth claim". Deterministic it is. But determinism is not the property under question — defensibility is, and "alphabetically first" is not defensible as a source hierarchy.

What would unblock it

Small fix, no new machinery. In _canonical, before the lexical fallback, order live rows by an explicit, declared key — content count descending, then an explicitly ranked origin list, then lexical as the final tiebreak — and emit that choice as an evidence record like every other decision. Lexical stays as the last resort so determinism is preserved. The point is not that content-count is the one true rule; it is that the rule should be chosen and stated rather than inherited from ASCII.

J2 — Is v2/v3/none the right seam? Right call one fix

Three modes is correct, and it is not hedging. The three are not speculative variants of one idea — they are three states that demonstrably exist in this estate right now: none is any partial database (the baseline found only people attachable locally out of five domains); v2 is production today; v3 is Lane 3/4, written and unmerged. Deleting none would mean crashing or silently lying on a partial attach; deleting v3 would mean this lane blocks on a merge it does not control — which is precisely the dependency that made v0 Prompt 5 unexecutable, per the handoff. Detection is by probing sqlite_master rather than reading a version number (capability.py:80-95), which is right for a database that has been additively upgraded.

The real economy is elsewhere and the PR gets it: four surfaces (CLI, API, MCP, viewer) hold zero SQL and are enforced by test_no_surface_contains_sql. That is the abstraction that pays.

Non-blocking fix — v3 is elected on table presence alone

capability.identity_mode() (capability.py:57-63) returns "v3" the moment identity_decision or identity_cluster exists — regardless of whether it has rows or matches the expected shape. Meanwhile V3Resolver admits it "has not been validated against a merged v3 database and is provisional." So an empty, half-migrated, or schema-drifted v3 table silently promotes every read onto the one adapter nobody has ever run for real.

Mitigating factors, which is why this is not blocking: V3Resolver extends V2Resolver so v2 signals still apply; the cluster lookup is wrapped in try/except sqlite3.Error (resolver.py:459 @ 3d648aa, which the fix commit changed from swallowing to reporting — defect 6); and the mode is reported on every response with a provisional warning. The failure is loud, not silent. Still — gate v3 on the table being non-empty, or on a shape probe, and fall back to v2 otherwise.

J3 — Is merging a latent fix correct? Yes — merge it

The case against. It changes nothing observable. Zero identity_claim rows means zero behaviour delta on real data, and 4,061 lines of new read surface is real review burden, real maintenance, and real risk of bitrot before the first claim ever arrives. A fix you cannot observe working in production is a fix you cannot prove works in production — every guarantee rests on synthetic fixtures.

The case for, which I find stronger. This is a deadlock, and the PR is the only way out of it. The baseline puts it precisely: the matcher never ran, so no claims exist; no read path consumed claims, so producing them was pointless work. Neither side moves first unless someone breaks the cycle, and the read side is the correct side to break it on — a read path that cannot honour a reviewer's decision is a defect whether or not a decision currently exists. Ship the consumer, and populating identity_claim becomes worthwhile for the first time.

Two things reinforce this. First, the baseline's D4 ("is this person the same as that account?") is the only one of five pre-registered decisions that is structurally unanswerable — not slow, impossible. Second, the safety argument: the README's feared "two John Murrays fuse into one" disaster has not happened, but as the baseline notes, that safety is accidental — it holds because the matcher never ran, not because a guard prevented it. 1,266 names are shared across rows. Landing the disciplined consumer before anyone turns on a matcher is the safe ordering. Reversing it — claims first, consumer later — is how you get silent bad merges.

Verdict: merge the latent fix (after J1), because it converts a deadlock into ordinary sequential work and it establishes the consumer's discipline before any producer can do damage.

J4 — Is a logical digest sufficient for reproducibility? Sound, with a measured blind spot

The choice of logical over byte identity is correct and well-argued. digest.py:4-29 names the actual sources of byte non-determinism — page allocation, freelist ghosts, the header change counter, WAL timing, sqlite_sequence — and measure_binary_stability() reports the byte answer as a measurement rather than assuming it. Every exclusion is justified in place rather than being an unexplained skip. This is the honest way to make the claim.

What could differ and still produce an identical digest — I tested rather than speculated

H1 schema-blind (different column types, different NOT NULL, same values): True   ← IDENTICAL DIGEST
H2 index-blind  (one DB has an extra index):                               True   ← IDENTICAL DIGEST
H4 separator collision (\x01 injected into a value):                       False  ← safe

H4 is clean — the type-prefix rendering in _render prevents delimiter attacks, so that class of hole does not exist. Good design.

But H1 and H2 confirm the digest is entirely schema-blind. _table_names (digest.py:89-104) reads sqlite_master for the name column only and never touches sql. Nothing anywhere in build_v3/ digests DDL. Therefore two builds are certified "logically equivalent" across: changed column types, dropped or added NOT NULL/CHECK constraints, changed defaults, added or dropped indexes, changed foreign keys, and table-vs-view swaps.

Also invisible: any table absent from both builds. The digest compares two artifacts to each other; it cannot notice that both are missing something the real graph has. That is exactly the J7 finding below.

Why this matters more here than it would elsewhere: the P0 this PR exists to fix is a schema defect. The baseline's §3.3 finding is that four shipped tables exist in no tracked schema. A reproducibility gate that cannot see schema drift is blind to the precise failure class it was built to prevent. Not blocking on its own — the digest does what it says for row content, and constraints are stable in practice — but it should be closed and it is cheap: hash the normalised sql from sqlite_master into the overall digest as a __schema__ pseudo-table, and add the H1/H2 cases as tests.

J5 — Does the 6-person / 56-row fixture mean anything at scale? Partly

The fixture is not meaningless. It proves the three things it was built to prove, and those are properties of logic, not of volume: timestamps are pinned rather than wall-clock, accumulation is REPLACE-keyed rather than rank_score = rank_score + x, and ties break by name rather than dict order. Each of those is scale-invariant — a build that depends on execution count does so at 56 rows and at 56 million. Testing them small is correct, not a shortcut.

What the fixture cannot see

1. Unbounded memory in the digest. digest.py:124 does SELECT <all cols> FROM <table> then .fetchall() — the entire table into a Python list — and :125 then builds a second full list of rendered strings and sorts it. I measured the ratio rather than guessing:

rows=200,000  db_bytes=7,598,080  peak_python_mem=60,751,798  ratio=8.00x

Eight times on-disk size, held live. The real graph's two largest tables alone (person_topic 2,050,629 + person_person 1,272,495 = 3.3M rows) extrapolate to roughly 1 GB peak, and the full 5.6M-row graph to ~2–3 GB. That is survivable on a dev box and would likely not crash CI, so it is not blocking — but it is an unbounded fetch that a 56-row fixture can never surface, and the fix is mechanical: stream with ORDER BY in SQL and hash incrementally instead of sorting in Python.

2. Nothing exercises the production path at all. The handoff admits this squarely — "only the fixture path is one-command", production "was not run here because no production corpus was available offline, and claiming otherwise would be fabrication." That is exactly the right way to state a limit, and I want to be clear that I am not penalising it. But it does mean the reproducibility claim is proven for --fixture and asserted for everything else.

J8 — The six fixes at 3d648aa, and whether the blind spot survives

I verified the fixes rather than taking them on trust. The suite runs 75/75 green (was 68), with one new file, tests/query_v3/test_review_findings.py, carrying 7 tests.

The fixes are real

The headline one — defect 1, a rejected pair staying merged — is properly closed. _contradicted_pairs (resolver.py:159-187) now queries status IN ('rejected','proposed') and the application point (resolver.py:262-277) refuses the union outright when a rejection exists, emitting a merge_refused record rather than silently dropping it. The reasoning is stated where the code is: "A rejected claim is an explicit decision NOT to merge and outranks a stale application." That is correct. Defect 2 is likewise closed — _merge_targets now walks both directions, with the docstring naming the exact symptom (the winner's page omitted the merged row's works, so the same person returned different data depending which name you typed).

Worth stating plainly: defect 1 meant the lane's headline guarantee — that only accepted decisions affect reads — was false as shipped. Finding that is what a cold review is for, and the author reproducing all six against the pushed clone rather than disputing them is the right response.

I note without irony that defect 6 was a swallowed sqlite3.Error — the same defect class this lane exists to fix (the bare except that hid the FTS breakage), one schema version later. That is a pattern worth naming in the handoff, not just fixing.

The blind spot: broken where it was tested, surviving where it was not

The author's root-cause diagnosis is exactly right and unusually clear-eyed:

its fixtures only ever built states where merged_into and identity_claim AGREED, so trusting merged_into alone was indistinguishable from checking both

That is a test suite that cannot detect the difference it is testing. So: do the new fixtures break the agreement? Partly. I measured both.

test_review_findings.py builds disagreeing states directly, with local INSERTs (:46-77) — r:rej-a merged into r:rej-b under a rejected claim. The blind spot is genuinely broken there, and those 7 tests do fail against the old code. Good.

But the shared fixture that the other 68 tests build on is unchanged. I enumerated every applied merge in it:

=== Every row with merged_into, and what the claim says ===
  gh:kant -> bk:kant (state=merged) | claim=accepted

=== any merged_into whose claim is NOT 'accepted'? ===

Still exactly one merged row, still in agreement. This is not blocking — the specific defects are fixed and proven fixed. J9 — The open judgement: applied merge + only a proposed claim

The author asked for this call explicitly and could not settle it. Current behaviour, verified empirically at 3d648aa:

PROPOSED + applied-merge -> canonical: r:pb   members: ['r:pa','r:pb']
   MERGED (not refused): True        # merges, and flags the inconsistency

My call: merge-and-flag is correct. Keep it.

The case for refusing is real and I want to state it at its strongest, because it nearly persuaded me. This module's whole thesis is that only accepted decisions affect reads. A proposed claim is by construction not accepted. Merging on a pair whose only decision record is a hypothesis looks like the module doing exactly what its docstring forbids — and the symmetry is seductive: if a rejection outranks a stale application, why shouldn't the absence of an acceptance?

It fails on three grounds.

  1. Refusing is also a decision, and a worse-evidenced one. A rejection is an explicit human statement that these are different people, so letting it beat a stale merge honours a real decision. A proposal states nothing — it is a hypothesis awaiting review. Treating "someone wondered about this pair" as grounds to override a merge a build actually applied gives a hypothesis more authority than an applied state. The resolver's own docstring already draws this line correctly: "A merely proposed claim over an applied merge is an inconsistent state that a caller must be told about, not one this module may resolve by picking a side." Refusing is picking a side.
  2. The asymmetry is principled, not arbitrary. Rejection and proposal are not two points on one scale. Rejection carries a decision; proposal carries a question. Outranking a stale application with a decision is honouring the review; outranking it with a question is inventing one.
  3. The failure modes are not symmetric in cost. Wrongly merging shows the caller one person with a loud unresolved flag — recoverable, and the flag is what prompts the review. Wrongly splitting silently reverts a merge the build applied, reintroducing the exact duplicate-rows defect (PG-AUDIT-002) this lane exists to close, on data where no reviewer ever said to split. That is a regression disguised as caution.

One condition on my answer: merge-and-flag is only right because the flag is loud. The current implementation satisfies that — the inconsistency surfaces in identity_resolution and raises a coverage gap. If that flag were ever softened to a log line or dropped, the calculus inverts and refusing becomes correct. Worth a comment at the flag site saying so, since the reasoning is not local to the code.

J6 — Do the two PRs conflict semantically? No conflict but a shared false premise

File paths are disjoint, as stated — query_v3/ + surfaces vs build_v3/ + loaders — and I found no semantic disagreement between them. On the contrary they compose well: #24's build_v3/paths.py is exactly the environment-override discipline #23's config.py wants, and #24's validator checks merged_into referential integrity (validate.py:129-130) which is a real invariant for #23's resolver. Merging both is coherent.

The shared problem is not a conflict between them but a premise both inherit: both treat schema/people_schema_v2.sql as the schema of record, and the baseline proves it is not. #23's fixtures build from it (tests/query_v3/fixtures.py:24-28); #24 builds and validates against it. For #23 this is a coverage gap and nothing worse: it never queries the four missing tables, so it is not wrong, merely narrower than production. For #24 it is the blocking item.

On the possibility that "ship it" was the right answer

It was not, but the margin is narrower than the finding count suggests. Across ~7,000 changed lines I found two blocking items, and one of them (#24) may be closable with a paragraph of honest documentation. The two blockers share a shape worth naming: each is a place where the code is correct but the claim around it is wider than the evidence — a policy presented as neutral that encodes an accidental hierarchy, and a P0 presented as closed that is half closed.
