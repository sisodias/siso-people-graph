GQ-010 Baseline — the measured before state

SISO People Graph · captured 2026-08-07, before any consolidation PR was merged · read-only

Why this document exists. GQ-010's own evidence_gaps[0] states: "There is no agreed baseline for current evidence-retrieval time, decision changes, or operator utility." Without a baseline, nothing downstream is measurable — the estate could merge every open PR and never know whether the 100× happened. Once those PRs land, the before-state is unrecoverable. This is that before-state, measured rather than asserted.

1. The five pre-registered decisions

Written to PREREGISTERED-DECISIONS.md before any query was run, so they could not be retrofitted to whatever the graph happened to answer well. GQ-010 success criterion #4 requires exactly this: "in at least five pre-registered operator or research decisions, the graph changes the selected action or reduces evidence-retrieval time by at least 80% against a measured baseline."

Read the timings correctly. Raw SQL against a local 1.1 GB file is fast — sub-second everywhere. The retrieval bottleneck for GQ-010's 80% target is therefore not query latency, and any future claim of "80% faster evidence retrieval" measured as SQL wall-clock would be measuring the wrong thing. The real cost today is the analyst work around the query: knowing which of several same-named rows is the right human (D4), and deciding whether a result is a person or an organisation (D1, D2). Those are the minutes-to-hours costs, and they are exactly what the empty claim layer fails to reduce.

3.3 The shipped graph cannot be built from the tracked schema

Four tables exist in the asset that appear nowhere in schema/people_schema_v2.sql: person_person, organisation, organisation_content, person_organisation. Between them they hold 1,287,159 rows — more rows than the entire tracked person table. The tracked schema is not the shipped schema.

And the largest of them is mislabelled. The release title calls them "person-to-person edges":

sqlite3 people_graph_v2.sqlite "SELECT relation,COUNT(*),MIN(confidence),MAX(confidence)
  FROM person_person GROUP BY 1;"
→ depends_on|1272495|0.95|0.95

sqlite3 people_graph_v2.sqlite "SELECT source,COUNT(*) FROM person_person GROUP BY 1;"
→ crates_io_dependencies|1272495
All 1,272,495 "person-to-person" edges are crates.io package dependencies projected onto owners at a flat 0.95 confidence. Package A depends on package B does not mean person A has any relationship with person B. This is a textbook instance of the consolidation plan's own diagnosis — the owner → creator category collapse — and the flat confidence means the number carries no discriminating information at all. Any downstream "social graph" or "who knows whom" feature built on this table is built on sand.

4. The findings that matter most

4.1 D4 is structurally unanswerable: identity_claim is empty

The README calls identity claims its central safety design: "Every proposed match is a row in identity_claim with a method, a confidence and the literal evidence." The table exists, is correctly designed, is indexed on status — and holds zero rows. Zero proposed, zero accepted, zero rejected. Nothing has ever been merged (merged_into non-null = 0; state='merged' = 0).

This is materially worse than the known defect. PG-AUDIT-002 / PGRT-004 is recorded as "ask.py never reads identity_claim" — implying claims exist but are ignored. Both halves are broken: ask.py contains no reference to identity_claim anywhere (verified by grep across all 357 lines), and there are no claims to read.

The consequence is visible in the live query. Asking the graph about Spinoza:

python3 loaders/ask.py --who "Spinoza"
→ "baruch-spinoza"                        kind=human, origin=registry, produced={}
→ "bk:spinoza, benedictus de|1632-1677"   kind=human, origin=books,    produced={book:13}
→ "gh:luisespinoza"                       kind=unknown, origin=github, produced={github:1}

The first two are the same human. The graph returns them as two unrelated matches, ranks neither, proposes no claim, and offers the operator no adjudication path. The third is a substring artifact of the LIKE fallback. An operator asking "is this the same person?" — the literal D4 question — gets no answer, and no mechanism by which an answer could ever be recorded.

One honest note in the graph's favour: the "two humans named John Murray would fuse into one" disaster the README warns about has not happened. Only two John Murray rows exist and they are correctly distinct. But that safety is accidental — it holds because the matcher never ran, not because a guard prevented it. Only 31 (platform,value) pairs map to multiple people, and 1,266 names are shared by more than one row. The blast radius is latent, not absent.

4.2 The README's headline limitation is wrong by 3,272×

The README's most-quoted claim: "Cross-domain stitch is 3. Not 3%, three people — Karpathy, Jensen Huang, Simon Willison." Measured:

sqlite3 people_graph_v2.sqlite "SELECT COUNT(*) FROM (SELECT person_id FROM person_content
  GROUP BY person_id HAVING COUNT(DISTINCT domain)>=2);"
→ 9818
Domain pairPeople
crates + github9,815
github + youtube_video3
youtube_channel + youtube_video1

The named three are exactly right (Karpathy, Huang, Willison) — but they are only the github+youtube pair. The crates_io load added 9,815 crates+github people the README never mentions. The true limitation is sharper and more interesting than the documented one: books overlap with nothing at all. Zero book+github, zero book+crates. The real statement is not "stitch is 3" but "the corpus splits cleanly into a living-software population that stitches well and a dead-books population that cannot stitch at all" — which the README's own analysis (20,246 book people died before 1950) actually explains, while its headline number contradicts.

Note also that 9,815 of the 9,818 come from a single source load, and both sides of that pair are kind='unknown'-dominated. This is breadth from one source class, not four — GQ-010 criterion #1 requires four distinct source classes.

4.3 PGRT-005 reproduced and quantified: a silent 130× slowdown

ask.py queries FTS with a schema-qualified table name, which SQLite rejects. The error is caught by a bare except sqlite3.Error and the code falls through to a LIKE scan. The query looks like it works.

SELECT ... FROM people.person_search s ... WHERE people.person_search MATCH ?
→ OperationalError: no such column: people.person_search   (caught, silently)

LIKE scan : 222.1 ms
FTS       :   1.7 ms

130× slower on the graph's single most common entry point, and the FTS index is fully built and functional — it is simply never reached. The schema comment predicted this exactly: "measured 57ms at 36k people, and it grows linearly." At 339k people it is now 222ms, tracking that prediction. This is the one place where a genuine, honest 80%+ retrieval-time improvement is available today, and it is a one-line fix.

4.4 PG-AUDIT-004 reproduced from a genuine clean checkout

git clone <repo> /tmp/pgclean && cd /tmp/pgclean
python3 loaders/build_people_graph_v2.py --v1 ... --out ...
→ FileNotFoundError: '/private/tmp/pgclean/loaders/people_schema_v2.sql'

The builder resolves the schema relative to loaders/; the file is tracked at schema/people_schema_v2.sql. A clean checkout fails on the first thing it does. Combined with §3.3 — four shipped tables absent from the tracked schema — the published graph is not reproducible from the published source at all, by two independent causes. GQ-010 criterion #6 (reproducibility) currently scores zero.

4.5 No rights, licence, or privacy field exists anywhere

sqlite3 people_graph_v2.sqlite "SELECT sql FROM sqlite_master WHERE type='table';" \
  | grep -ci "rights\|licen\|privacy\|consent"
→ 0

GQ-010 criterion #5 requires that "every promoted observation has an explicit rights state." No table has a rights, licence, privacy, or consent column. The criterion is not partially met — it is unrepresentable in the current schema. 35 people are living (death_year IS NULL AND birth_year > 1950) and carry no rights state; the practical exposure is small today, but the structural gap is total and every new source pilot inherits it.

4.7 What genuinely works — do not break these

An honest baseline records strengths, because the merge could regress them.

Roles are correctly on the edge, not the person.
Gutenberg gid 54161 carries Cicero as author and Featherstonhaugh as translator — the same work, two people, two roles, no flattening. 12 distinct roles in use. This is the design decision the README defends, and it is genuinely implemented.
Source attribution is complete.
Zero edges with a missing or unknown source, across 901,524 rows.
BCE handling is correct.
Plato stored as -428 → -348; v_contemporaries returns 16 rows for him. Century filters over the classical corpus work.
Fetchability is real.
fetchable() returns a live Gutenberg URL for every book edge, so an answer routes to actual bytes on a machine holding none of the corpus.
Nothing derived is stored, and no bad merge exists.
No stamped tier alongside score, so the 96.6% contradiction failure of the sibling system is avoided by construction. merged_into non-null = 0.

6. What I could not measure, and why

Stated explicitly so no future reader mistakes silence for a passing grade.

Identity-resolution precision, recall, and abstention.
Undefined at baseline, not merely unmeasured. With identity_claim empty, there are no accepted links to score. A future 99.5% precision claim will have no baseline to beat — it starts from an empty set, which is a measurement trap worth flagging now.
Human evidence-retrieval time.
I measured machine query latency, which is sub-second and not the bottleneck. The real operator cost — deciding which of several same-named rows is the right human — requires timing a human or an agent on the task, which I could not do read-only in one session. Any future "80% faster" claim must measure the analyst loop, not sqlite3 wall-clock, or it will be measuring a number that was already fast.
Whether graph-v2 is reproducible from any commit.
I proved HEAD cannot build it. I did not search history for a commit that could, because §3.3 shows four shipped tables exist in no tracked schema on this branch — so no commit on main can produce the asset. Whether an unmerged branch can, I did not test.
Cost and refresh budget.
No declared per-source acquisition budget exists, so criterion #6's cost half has nothing to compare against.
The other three open PR branches' effect.
Out of scope by C1 (read-only) and by design — this is the before picture.
Book Library and GitHub identity databases.
ask.py resolves five domains; only people was present locally, so cross-database routing was exercised for one domain rather than five.

8. The one-paragraph version

The SISO People Graph as shipped on 2026-08-07 holds 339,217 people and 901,524 content edges, and the person count — long treated as an unverified repository claim — is correct; it simply lives in a release title rather than a file. Of five pre-registered real decisions, it fully answers two, partly answers two, and cannot answer the identity question at all, because identity_claim — the table the project describes as its central safety design — is empty. Its documented headline limitation ("cross-domain stitch is 3") is wrong: the real figure is 9,818, and the true limitation is sharper — books overlap with nothing. Its 1.27M "person-to-person edges" are crates.io package dependencies at flat 0.95 confidence, not relationships between humans. 86.7% of rows do not know whether they are a person or a company. The graph cannot be rebuilt from its own source by two independent causes, no rights field exists anywhere, and the query surface silently runs 130× slower than the index it already built. What genuinely works — roles on the edge, 100% source attribution, BCE handling, reversible-by-construction merges, fetchable routes — is real and should be protected through the merge. Against GQ-010's six criteria the baseline is 0 of 6, with falsifiers F3 and F5 already firing. That is the line every future 100× claim gets measured against.
