Identity resolution — first contact with the real graph

People Graph v2 · run 2026-08-08 by PG-IDENTITY-RUN · asset SHA-256 9938237a…d9b919b · repo base 88858bc

Headline. The identity engine had never been run on real data. Running it found that every one of the 159 auto-accept candidates in the shipped graph is a false positive, and applying the documented automatic policy fuses 18 distinct named humans into a single person. Measured auto-accept precision on production data is 0.000, against the method card's synthetic-fixture claim of 1.000. The cause is a sentinel value — github_id=0 meaning "no GitHub account" — being treated as a unique identifier. A guard is included in this branch; after it, auto-eligible candidates go 159 → 0 and the engine is safe to run.

3. The defect: absence encoded as identity

The automatic path is shared_external_id only, so the entire auto-accept surface of this graph is whatever values are shared under an auto-eligible scheme. Measured, that surface is two values, both sentinels:

sqlite3 DB "SELECT value, COUNT(DISTINCT person_id) np FROM external_ids
            WHERE platform='github_id' GROUP BY value HAVING np>1;"
→ 0  | 18      → C(18,2) = 153 pairs
→ -1 | 4       → C(4,2)  =   6 pairs
                            ───────────
                             159 pairs   ← 100% of auto-eligible candidates

These are crates.io-derived rows for authors with no linked GitHub account; the loader wrote 0 or -1 rather than NULL. The people are unrelated:

All five auto-accept conditions pass for these pairs. The method is shared_external_id (1); github_id is registered unique and eligible (2); the rows are all kind='unknown' so no human/organisation flag fires, they carry no life dates so no date conflict fires, and they share no other unique scheme so no identifier conflict fires (3); joining them introduces no second value for a unique scheme, because they all carry the same one (4); and no prior rejection exists (5). The gate is working exactly as designed and specified. The specification is what is wrong.

Demonstrated, not argued

The unguarded policy was applied to a throwaway copy. After 72 accepts:

canonical_entity_id | members
gh:ghost_1185       |   18     ← 18 distinct humans, one "person"
gh:ghost_1356       |    4

This is GQ-010 falsifier F2 ("auto-accept precision below 99.5%, or silent merges") firing on real data on first contact, and it is exactly the disaster the README warns about ("two humans named John Murray would fuse into one"). The baseline noted that safety was "accidental — it holds because the matcher never ran". Running it confirms that reading.

4. Reversibility holds — the design's best feature

Undo was proven against the damaged database before any fix was written:

BEFORE undo: multi-member clusters = {'gh:ghost_1185': 18, 'gh:ghost_1356': 4}
active decisions: 72
undone: 72
AFTER undo:  multi-member clusters = {}
remaining active decisions: 0
source entities intact: 339217

Undo restored the prior state exactly and deleted no source rows. Cluster membership is recomputed from active decisions and each accept writes a new immutable generation, so every merge in this system is reversible in practice, not just in principle. This is the reason a 0.000-precision defect is recoverable rather than fatal.

5. The fix

A sentinel is a value that is syntactically valid for its scheme but encodes absence. The guard lives in registry.py, beside the rest of identifier policy, and blocks at two points:

  • Generation — a sentinel value never enters the shared-identifier index, so no auto-eligible candidate is ever minted from one.
  • Acceptance — defence in depth: a candidate minted before this guard existed still cannot auto-accept, so stored candidates from an earlier run stay safe.

Covered: github_id ≤ 0 and non-numeric, github_node_id=0, all-zero ORCID, Q0, and the text sentinels none/null/nil/n-a/unknown/ghost/deleted/deleted-user/anonymous/placeholder.

The 18 new tests include a reproduction of the exact production failure (three distinct humans sharing github_id=0 must yield zero auto candidates) and its inverse (two rows sharing a real GitHub id must still yield one), so the guard cannot silently over-block.

The honest consequence. With the guard in place this graph has zero safe auto-accept candidates. That is the correct outcome, not a disappointing one: the auto path requires shared authority identifiers, and the graph holds only 806 ORCIDs, 805 Wikidata QIDs and 35 YouTube channel ids — none of them shared between two rows. Automatic identity resolution here is blocked by source coverage, not by algorithm quality. Adding real authority identifiers is what unlocks it.

The most instructive rejection

The single name_plus_years candidate — the highest-confidence review item in the entire graph at 0.86 — is wrong:

bk:kernahan, coulson, mrs|1857-1941   "Kernahan, Coulson, Mrs."   1857–1941
bk:kernahan, coulson|1858-1943        "Kernahan, Coulson"         1858–1943

Dates fall inside the ±2 tolerance and the comparison keys are identical — because normalize_name strips Mrs. as a noise token. These are spouses: the novelist Coulson Kernahan and his wife, who published as "Mrs. Coulson Kernahan". They hold separate authorship (1 work vs 5). 248 book rows carry an honorific, so this failure mode has a real population. Stripping honorifics before comparison makes married couples collide — the gate correctly refuses to auto-accept it, but it ranks first in the review queue.

7. What genuinely works

  • The conflict guard is effective. 12,834 same-name crates pairs are correctly blocked by conflicting_github_id. Where people have real distinct GitHub ids the guard catches them — the precise inverse of the sentinel bug.
  • The human/organisation guard works. 64 pairs blocked, e.g. "Street, Julian" vs "Jane Street", "Lang, T. B." vs "triton-lang".
  • Deny-by-default holds. 303,683 github_login and 68,324 crates_io values were correctly quarantined as aliases/unregistered and never drove a candidate.
  • Reversibility is real (§4).

9. What I did not do, and why

  • Did not bulk-accept. Constraint C6 fired: measured precision (0.000) is below the method card's claim (1.000). Post-guard there is nothing left to auto-accept anyway.
  • Did not accept any name-only candidate without corroboration. 7 of the 9 reviewed were rejected. surname_initial (14,501 candidates, 0/20 precision) should be considered for removal or demotion — it is the largest method by volume and produced no true positive.
  • Did not retry the github↔book stitch. Packet says structurally dead; the run confirms it — zero book candidates survived review, and all 9 book-origin pairs reviewed were artifacts.
  • Did not touch PR#23/#24, and did not merge. Branch pg/identity-run-20260808, draft PR only.
  • Did not write to the published asset or to ~/foundry-data.

Known limits of this run

  • Precision figures are from strata I reviewed by hand (9 + 20 + 1 + 159 pairs), not a probability-weighted sample of all 29,366. The exact_name figure covers the cross-origin human↔human stratum specifically; the 12,834 crates↔crates same-name pairs are blocked by conflict and were not individually reviewed.
  • Non-Latin script coverage was inspected but is thin — the graph's non-Latin rows are almost entirely book-origin, which stitches with nothing, so script handling is largely untested by this corpus.
  • Each accept writes a full generation (339,217 membership rows, ~48 MB). Correct for undo, but this will not scale to thousands of decisions — 72 accepts grew the database from 258 MB to 3.7 GB. A production run needs batched acceptance with one generation per batch.

10. Recommended next steps

  1. Merge the sentinel guard before anything else runs the engine. It is the only thing standing between this graph and an 18-person false merge.
  2. Fix the loader so absent GitHub accounts write NULL, not 0/-1, and audit other loaders for the same pattern.
  3. Batch acceptance — one generation per batch, not per decision.
  4. Demote or remove surname_initial pending evidence it produces any true positive.
  5. Stop stripping honorifics before name comparison, or treat an honorific difference as negative evidence (248 affected rows).
  6. Add authority identifiers (ORCID/VIAF/Wikidata) to more rows — that, not algorithm work, is what unblocks automatic resolution here.
